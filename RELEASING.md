# Выпуск релиза — чек-лист

Полное объяснение схемы версий — в [README.md](README.md#versioning). Этот
файл — только порядок действий, чтобы не перепутать при выпуске.

## 1. Определить, какое число бампить

Версия — `Major.Minor.Build.Revision` (например `0.1.1.0`):

| Число | Название | Когда бампить |
|---|---|---|
| 1 (Major) | Релизы | Крупная версия для ВСЕХ пользователей |
| 2 (Minor) | Обновления | Собранный набор готовой, связанной работы (новые функции + фиксы) |
| 3 (Build) | Фиксы | Багфиксы, найденные по ходу активной разработки |
| 4 (Revision) | Дебаг-тесты | **Только** для проверки самого механизма обновления — см. правила ниже, никогда не для настоящего релиза |

Бампится **только** нужное число, всё, что ПРАВЕЕ него, обнуляется (пример:
Фикс — `0.1.0` → `0.1.1`, а не `0.1.0.1` — четвёртое число не для этого).

## 2. Настоящий релиз (Major/Minor/Build)

1. Обновить `<Version>` в
   `src/BrightnessControl.App/BrightnessControl.App.csproj`.
2. `dotnet build` и `dotnet test
   tests/BrightnessControl.Core.Tests/BrightnessControl.Core.Tests.csproj`
   — оба должны быть 0/0 и все тесты зелёные.
3. Закоммитить bump отдельным коммитом ("Bump version to X.Y.Z").
4. Собрать self-contained exe:
   `dotnet publish src/BrightnessControl.App/BrightnessControl.App.csproj -p:PublishProfile=win-x64`
   (артефакт — `.../publish/win-x64/BrightnessControl.App.exe`, обычно
   ~55 МБ; framework-dependent `dotnet run`/`dotnet build`-сборки для
   реального релиза НЕ годятся — не самодостаточны).
5. Создать релиз на GitHub, тег **`vX.Y.Z` без суффиксов**
   (`Version.TryParse`, используемый `UpdateCheckService`, не понимает
   суффиксы вроде `-beta` — реальный баг, встреченный при тестировании
   Фазы 6). `draft: false`, `prerelease: false`.
6. Загрузить asset с именем **строго `BrightnessControl.exe`** (см.
   `UpdateCheckService.ExpectedAssetName`) — под другим именем
   автообновление его не найдёт.
7. Убедиться, что GitHub вернул `digest` (sha256) у загруженного asset —
   на нём основана проверка контрольной суммы в `SelfUpdateService`.

## 3. Дебаг-тестовый релиз (Revision, только для проверки механизма обновления)

Используется ИСКЛЮЧИТЕЛЬНО чтобы проверить скачивание/переименование/
перезапуск на реальном GitHub-релизе — не для пользователей.

1. Тег тоже **без суффиксов** (та же причина, что и выше).
2. `prerelease: true` — обязательно, иначе релиз увидят пользователи на
   канале "Все версии" без включённой галочки "Включать бета-версии".
3. После проверки — **удалить и релиз, и тег** (`DELETE
   /repos/.../releases/{id}` и `DELETE
   /repos/.../git/refs/tags/vX.Y.Z.R`). Дебаг-тестовые релизы не должны
   накапливаться в списке Releases репозитория.

## Известные грабли

- Правка публичного УЖЕ созданного релиза (например переименование тега)
  требует явного разрешения пользователя — авто-режим блокирует такие
  правки как "Create Public Surface".
- Версия в `.csproj` без явного четвёртого числа (`0.1.1`, не `0.1.1.0`)
  — MSBuild сам дополняет `AssemblyVersion`/`FileVersion` до 4 частей,
  ничего вручную дописывать не нужно.
