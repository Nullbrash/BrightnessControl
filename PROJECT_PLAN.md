# BrightnessControl — проектный план

Desktop-приложение для Windows 11: управление яркостью подключённых
мониторов (по отдельности и всех сразу), с трей-доступом и
автоматизацией по сценариям.

Порядок работы над проектом подчиняется иерархии планирования:
проектный план (этот файл) → функциональный план (`.plans/PLAN_<slug>.md`,
только локально, в `.gitignore`) → фазы → этапы → пункты/вопросы.
Каждая фаза функционального плана начинается с вопросов пользователю и
не выполняется без подтверждения.

## Идейные столпы

1. **Универсальное управление яркостью** — единый API "яркость по
   монитору" и "яркость всех сразу". Источники: DDC/CI (внешние
   мониторы), WMI/`WmiMonitorBrightnessMethods` (встроенная панель
   ноутбука), программный fallback (например, gamma-коррекция или
   оверлей-затемнение) для мониторов без поддержки DDC/CI — это не
   гипотетический, а реальный кейс в имеющемся оборудовании.
2. **Мгновенный доступ через трей** — иконка в трее, скролл колеса мыши
   над ней меняет глобальную яркость. Поведение скролла (вкл/выкл,
   "проценты 0–100" против "циклическое переключение между
   пресетами") — настраивается, а не жёстко зашито.
3. **Полноценный GUI (Avalonia)** — детальная настройка каждого
   монитора, групповое управление, отдельная категория настроек
   "Поведение трея". Любое окно, открытое из трея (клик/меню),
   обязано появляться на том мониторе, где физически произошло
   взаимодействие, а не только на основном мониторе системы.
4. **Контекстная автоматизация** — три вида правил:
   - расписание по времени суток;
   - профили яркости, привязанные к активному приложению/окну;
   - адаптивное затемнение по бездействию: настраиваемый idle-таймаут
     (в минутах) → приглушение яркости → автоматическое восстановление
     исходных значений при возврате активности пользователя.
5. **Устойчивость к разнородному оборудованию** — программный fallback
   обязателен для мониторов без DDC/CI, а не опционален.
6. **Гибкое хранение настроек** — при первом запуске пользователь
   выбирает режим: portable (конфигурация рядом с exe) или обычный
   (в профиле пользователя, `%AppData%`). Выбор сохраняется.

## Технологический фундамент

- **Целевая платформа: Windows 10 версии 2004 (сборка 19041, "May 2020
  Update") и новее, включая Windows 11.** Заявлено официально
  (2026-09-15) — `TargetFramework` (`net9.0-windows10.0.19041.0`) и
  `app.manifest` (`supportedOS` — Windows 10 GUID) уже были
  технически совместимы с этой границей, ничего в коде не использует
  Windows-11-эксклюзивных API; сама заявленная граница расширена с
  «только Windows 11» по итогам проверки. Живого теста именно на
  Windows 10 пока не было — граница технически обоснована, но не
  подтверждена на реальном железе. Кроссплатформенность за пределами
  Windows не является текущим требованием, но при прочих равных
  предпочитаются решения, не закрывающие путь к будущему переносу.
- **GUI-стек: Avalonia** (XAML/MVVM, как WPF, но кроссплатформенный по
  своей природе; включает системный трей API). WPF был отклонён
  осознанно — он исключительно для Windows и потребовал бы полного
  переписывания GUI-слоя при будущем портировании.
- **Язык/платформа:** C#/.NET (актуальная LTS-версия), финальный
  артефакт — `.exe` под Windows.
- **Яркость:** DDC/CI (внешние мониторы) + WMI (встроенная панель) +
  программный fallback (мониторы без DDC/CI).
- **Версионирование:** 4 числа `Major.Minor.Build.Revision`, каждое со
  своим смыслом (Релизы/Обновления/Фиксы/дебаг-тесты) — решено в
  FP7/FP16, подробности в `README.md` (раздел "Версионирование").
  Кроссплатформенность — отдельное измерение, которое пока не в фокусе.
- **Git:** репозиторий
  [Nullbrash/BrightnessControl](https://github.com/Nullbrash/BrightnessControl)
  на GitHub (переименован из `GlukozaLCD/BrightnessControl`).
  Функциональные планы (`.plans/PLAN_*.md`) в репозиторий не попадают.

| FP10 | готово (2026-09-10) | Визуальный конструктор автоматизации | Объединяет триггеры по времени (бывший FP4) и по процессу (бывший FP5) в один список правил `AutomationRule`/`AutomationEngine` (Core) — обе старые системы (`ScheduleEngine`/`AppProfileEngine`) удалены целиком, не оставлены даже параллельно ("чистый лист", явное решение пользователя). Правило — один узел с внутренними условиями (форма, не граф — полноценный Blockly-подобный конструктор блоков признан непропорционально дорогим для домена из ~2 типов условий, оценка сделана по явному запросу пользователя, с примерами макетов). Условие по времени — набор непересекающихся отрезков `TimeSegment` в минутах от полуночи (НЕ `TimeOnly` — иначе невозможно честно представить "24:00", последние минуты суток терялись бы), опционально И/ИЛИ условие по процессу; приоритет по умолчанию — порядок в списке (правила можно двигать местами), либо явное число, которое побеждает абсолютно. Условие по времени выбирается перетаскиванием отрезков на линейке (ЛКМ создаёт/двигает/тянет край, ПКМ удаляет, слияние при пересечении) вместо числовых полей — несколько раундов макетов (Artifact) перед реализацией. Вкладка "Автоматизация" в `SettingsWindow` полностью заменяет старые "Расписание"/"Профили приложений"; карточка правила поддерживает редактирование на месте (без потери позиции в списке — позиция участвует в приоритете), кнопки встроены в стены самой карточки (тот же приём, что и у галереи форм иконки трея), с диагональным/вертикальным бликом (та же техника ручного `DispatcherTimer`, что у кнопки закрытия программы), кликабельный кружок вкл/выкл вместо чекбокса.
